# Brasscribe Play for Android

Kotlin and Jetpack Compose. Android 10+ (min SDK 29, for AudioPlaybackCapture), target SDK 36, compile SDK 37 (Compose 1.12 requires it). Gradle Kotlin DSL with a version catalog (`gradle/libs.versions.toml`).

## Build and test

```
export ANDROID_HOME=/opt/homebrew/share/android-commandlinetools   # SDK: platform 37, build-tools 36, NDK 28.2, CMake 3.31.6
./gradlew assembleDebug testDebugUnitTest testFretscribeDebugUnitTest lint   # the screens too, on the JVM (Testing)
apps/android/scripts/device-tests.sh smoke   # emulator or device
./gradlew assembleRelease                    # both apps: one APK per ABI plus a universal one, unsigned
```

`testDebugUnitTest` also runs the tests of the plain Kotlin modules. The JVM tests of the app need the host build of the core (`cargo build --release -p brasscribe-ffi` in `core/`, or `scripts/core-artifacts.sh ensure host`).

The `app` module builds two apps from the same code, as the product flavours `brasscribe` (the default) and `fretscribe` (`no.fretscribe.play`), so its variant tasks carry the product's name: `assembleFretscribeDebug`, `assembleFretscribeRelease`, `lintFretscribeDebug`, `testFretscribeDebugUnitTest`. `testDebugUnitTest`, `installDebug`, `connectedDebugAndroidTest` and `lint` mean the Brasscribe app; `assembleDebug` builds both. The APKs are in `app/build/outputs/apk/<product>/<build type>/`. What differs between the two is in `app/src/brasscribe` and `app/src/fretscribe` (`Product.kt`, the app's name and its own words, the window colours, and Fretscribe's screens under `fret/`) and in the design each is built with (below); everything else is in `app/src/main`. The band SoundFont and the on-device models are Brasscribe's, so the Fretscribe APK does not carry them. Fretscribe has the version in `defaultConfig` too, unless a build is given another (`-Pfretscribe.versionName=… -Pfretscribe.versionCode=…`): today the two are released together ([Releases](#releases-and-updates-on-a-phone)).

Some inputs come from outside git and are used only when present:

| Input | From | Used for |
|---|---|---|
| `models/converted/{swift-f0/swift-f0-window.onnx, basic-pitch/nmp-b1.onnx, beat-this/beat-this-small0.onnx}` | `convert/` (all MIT) | Bundled in every build: the offline solo (SwiftF0 spine, Basic Pitch confirmation, Beat This! small beats) and the band draft (Basic Pitch on the mix, Beat This! small). Without SwiftF0, "On this phone" is disabled for a solo; without the other two, a solo's notes stay unconfirmed and its grid is a steady tempo, and no band draft is offered |
| `core-bridge/src/main/jniLibs/` | `scripts/build-core.sh` (cargo-ndk, arm64-v8a + x86_64) | The Rust core. Without it `AppContainer.core` is the Kotlin fallback. The JVM tests of `core-bridge` load the host build (`cargo build --release -p brasscribe-ffi` in `core/`) and skip without it |
| `third_party/onnxruntime/onnxruntime-android-reduced.aar` | `scripts/ort/build-reduced-ort.sh <work dir>` (builds both ABIs, then merges them into the AAR) | Reduced-operator ONNX Runtime 1.30.0 (only the kernels of the three models, `scripts/ort/ops.config`). Without it the full Maven build is used |
| `data/golden/mikkel-arranged-band/` | the golden output | JVM tests only (never packaged). Tests that need it skip themselves when it is missing |
| `third_party/sfizz` | `scripts/fetch-sfizz.sh` (sfizz 1.2.3) | The realistic playback tier. Without it the native library builds a stub and the tier is shown as unavailable. | `data/sounds/band/brasscribe-band-mobile.sf2` | `pixi run fetch-sounds` at the repository root (the pack pinned in `sounds/band-sounds.json`; needs `gh auth login`) | Bundled in every build as `assets/sounds/` (68 MB with `sounds-2026.09.30`): the band plays its own instruments with no download. Without it the app says the band sounds are missing. Release builds in CI fetch it first and stop if they cannot |

## Releases and updates on a phone

Every GitHub release of this repository carries both apps, each as an APK for arm64 phones and a universal one (`.github/workflows/android.yml`, on a `v*` tag; [docs/dev/release.md](../../docs/dev/release.md)):

| App | Package | Files | Signed with |
|---|---|---|---|
| Brasscribe Play | `no.brasscribe.play` | `brasscribe-play-android-arm64-v8a.apk`, `brasscribe-play-android-universal.apk` | Brasscribe's own key (alias `brasscribe`) |
| Fretscribe | `no.fretscribe.play` | `fretscribe-android-arm64-v8a.apk`, `fretscribe-android-universal.apk` | a key of its own, shared with other prototype apps (alias `prototypes`) |

A key never changes, or the phone refuses the update; the signing job checks each APK's certificate against its app's, and fails if a file carries the other app's. Both apps have the release's version today (`versionName` is the tag without its `v`, and `versionCode` goes up by one with every release: `scripts/release.sh`); the workflow's `fretscribe_version_name` and `fretscribe_version_code` inputs give Fretscribe one of its own. A Fretscribe release build has the Rust core, an audio library without sfizz, and neither the band SoundFont nor the on-device models; the build job checks that too.

**Obtainium** installs and updates an app from these releases. With two apps in one repository, each is added as its own app from the same address (`https://github.com/181192/brasscribe`), told apart by a filter on the APK's file name. Under **Filter APKs by regular expression**:

| App | Filter |
|---|---|
| Brasscribe Play | `^brasscribe-play-android-arm64-v8a\.apk$` |
| Fretscribe | `^fretscribe-android-arm64-v8a\.apk$` |

The shorter `brasscribe-play-android-arm64` and `fretscribe-android-arm64` do the same: neither file name contains the other's. An entry for Brasscribe from before Fretscribe was in the releases needs its filter if it has none (or one as wide as `arm64`), as a release now has two arm64 APKs. Obtainium takes the version from the release's tag.

A phone that has a debug build of the app must have it uninstalled first: it is signed with another key, and its songs go with it.

## Modules

| Module | Kind | What it holds |
|---|---|---|
| `model` | Kotlin/JVM | Composition JSON model (tolerant of new fields), tick map (bars and recording seconds, including the golden file's negative `first_downbeat`), spelling and brass-band transpositions, `PartView`, a monophonic MusicXML writer, a solo quantizer with key and tempo estimates, and the talking-score announcer. `CoreBridge` is the seam for the Rust core |
| `engine-client` | Kotlin/JVM | Ktor client for `engine/openapi.json` (pairing, upload, jobs, SSE progress, results, the recording a job was made from, and the `tab` profile's options and its `Tab`), `ProgressTracker` for the time left, and `FixtureEngineApi` (replays a finished engine output folder with timed stage events, for tests) |
| `pitch` | Kotlin/JVM | SwiftF0, Basic Pitch and Beat This! small on ONNX Runtime (the `ai.onnxruntime` API: the Android build in the app, the desktop build in tests), with their host code ported (SwiftF0 windows and `segment_notes`; Basic Pitch windowing and note decoding; Beat This log-mel, chunking and minimal postprocessor), the resampler, `SoloPipeline` and `BandDraftPipeline` |
| `core-bridge` | Android library | `RustCoreBridge`: the UniFFI Kotlin bindings from `core/android` plus `libbrasscribe_ffi.so`, behind `CoreBridge` |
| `audio` | Android library with NDK | Decoding audio and video with MediaExtractor/MediaCodec, WAV, microphone capture through Oboe/AAudio, AudioPlaybackCapture, sfizz playback through an Oboe output stream |
| `app` | Android app | Compose UI, capture and band-draft foreground services, alphaTab score, exports |

## Seams

- **CoreBridge** (`model/.../CoreBridge.kt`). `RustCoreBridge` (core-bridge) is the default: ps13 spelling, the layered arranger for solo takes with lineup, difficulty, key and transposition, re-arranging a Composition with the same options (`arrangeMusicXmlWith`, after a note is changed and on How should the score be?), the announcer (all 25 talking-score vectors pass through it, EN and NB), the per-part talking score of arranged MusicXML, and humanization. `KotlinCoreBridge` is the fallback when the native library is missing; it has no arranger, per-part talking score or humanization.
- **Engine client.** The client is hand-written. `openapi-generator` 7.25.0 (kotlin, jvm-ktor, kotlinx_serialization) produced code that does not compile for this spec: `additionalProperties: true` became `HashMap<String, Any>()()`, numbers became `@Contextual BigDecimal`, and the SSE stream was typed as a JSON body. `EngineContractTest` compares the client with the vendored `engine-client/openapi.json`: operationIds, every property, required fields and enums. Refresh the spec with `./gradlew :engine-client:syncOpenApi` once `engine/` is in the same checkout.
- **Tab** (`engine-client/Tab.kt`) is the client's side of the `tab` profile: one fretted instrument (`FrettedInstrument`: the basses, the guitars, the ukuleles and the mandolin, each with its tunings and its preset ids in the core's crate). Fretscribe sends its jobs and reads its result (below). `bass-tab` is the same profile's id for a bass in older apps: jobs made by them still carry it, and `Profile.writesTab` is true for both. A tab job takes `TabOptions` (instrument, tuning, capo, style, recording, octave, layout, chords; one left out is not sent, and the engine uses its default), and its result is `tab(jobId)`: a string and a fret for every note, with what the song check shows and what was left out or added. `musicXml`, `pdf` and `midi` serve `tab.*` for such a job (the PDF and the MIDI only when the computer has MuseScore). The API's enums decode a value from a newer engine as `UNKNOWN` instead of failing the answer. `EngineException.refusal` names the engine's refusal codes, among them `CORE_MISSING` (the computer's Brasscribe cannot write tab). `apps/fixtures/bass-line`, `guitar-line` and `ukulele-line` hold what the engine answered for a job on a short synthesized take of each (`apps/fixtures/make-bass-line.py` and `make-fretted-lines.py` record them again), and `FixtureEngineApi` replays them. A fixture with a `profiles.json` (a list of profile ids) plays a computer that has only those, as one from before the `tab` profile does.
- **On-device models.** SwiftF0, Basic Pitch and Beat This! small run on ONNX Runtime (one runtime for all three; Basic Pitch's TFLite would need LiteRT as a second runtime). Parity with upstream, JVM tests: SwiftF0 0.00 cents and 36/36 notes; Basic Pitch note F1 1.000 (synthetic and URMP March); Beat This beat/downbeat F1 1.000/1.000 on clicks and URMP, 1.000/0.986 on Mikkel 60–120 s.
- **No telemetry from ONNX Runtime.** Microsoft's AAR reports to Microsoft (`mobile.events.data.microsoft.com`): its manifest adds the content provider `ai.onnxruntime.TelemetryInitializer`, which, before the app starts, sets up an uploader that reads the device's `ANDROID_ID`, maker and model and follows the network and the battery; the runtime then sends an event when it starts. Nothing may leave the phone but what goes to the player's own computer, so the app's manifest removes the provider (`tools:node="remove"`) and `PlayApplication.attachBaseContext` sets `ORT_DISABLE_TELEMETRY=1`, each enough on its own. `verifyNoTelemetry<Variant>` (run by every `assemble`, `package`, `bundle`, `install` and unit-test task) fails the build when any ONNX Runtime component is in a merged manifest, and `OrtTelemetryDeviceTest` (`connectedDebugAndroidTest`) checks the installed app while the pitch model runs. `ACCESS_NETWORK_STATE`, which the AAR also asks for, stays: `MainActivity` follows the network to reach the computer again. The reduced runtime is built with `--no_telemetry`.
- **No Google components: the pairing QR code is read on the phone.** The app used to scan it with Google's code scanner (`play-services-code-scanner`). That library logs ML Kit usage to Google: when the scanner opens, the app's own process stores a `FIREBASE_ML_SDK` event in Google's datatransport queue (`databases/com.google.android.datatransport.events`) and schedules `JobInfoSchedulerService` to upload it to `firebaselogging.googleapis.com/v0cc/log/batch` (seen on an emulator with Google Play services: the event and the job when the scanner opened; the job, which would otherwise have run within a day once the network allowed, was started by hand and its upload was answered 200). The scanning screen itself is Play services' (`com.google.android.gms.mlkit.ACTION_SCAN_BARCODE`): the scan runs in Play services' process, out of the app's control, and Play services receives the pairing code. Google's [ML Kit terms](https://developers.google.com/ml-kit/terms) say the APIs "send metrics about the performance and utilization of the APIs in your app to Google", its [data disclosure](https://developers.google.com/ml-kit/android-data-disclosure) lists device and app details and identifiers, and neither documents a way to turn it off (nor does the library read such a setting, as far as its classes show); removing the datatransport components from the manifest would leave the Play services side. So the app reads the code itself: CameraX shows the camera and ZXing (`connection/QrDecoder.kt`) decodes each frame on the phone, taking the first code in view that is a pairing link and passing over any other; nothing is kept or sent. A camera that can't be opened, or stops (taken by another app, turned off by policy), says so and leaves typing the code. On a phone updated from a version with the Google scanner, `GoogleLeftovers` deletes at start what ML Kit left (its queue of events, `databases/com.google.android.datatransport.events`; its install id, `shared_prefs/com.google.mlkit.internal.xml`; and the upload's scheduled job), and the backup rules leave them out. It needs the camera permission, which is asked on the scanner's screen, where it says what the camera is for; refused, the screen says so, offers the app's settings and leaves typing the code. `verifyNoTelemetry<Variant>` (above) also fails the build when an ML Kit, Play services, Firebase or datatransport component is in a merged manifest, or a library of theirs is on the variant's runtime classpath. Its tests are `QrDecoderTest` (`app/src/test`: the pairing link read from camera-like frames, padded rows, light on dark, on its side, next to another code), `GoogleLeftoversTest` and `PairByScanTest` (`app/src/screenTest`, both apps, with `ShownQrCode` in place of the camera: a code read goes to pairing, a code that is not a pairing link says so, Cancel, the camera refused and allowed when asked).
- **The offline solo** (`pitch/SoloPipeline.kt`) is the engine's rule through the layered arranger with only a solo layer: SwiftF0 is the spine, Basic Pitch fills both confirmation slots (MuScriptor's too), the SwiftF0 contour gives written durations, Beat This the beats. Each layer's MIDI is written at its adapter's resolution (SwiftF0 480, Basic Pitch 220 ticks per beat at 120 bpm), so onsets round like the reference. On the URMP Entertainer trumpet clip (`data/runs/apple/entertainer-ref`, minimal lineup) it matches the reference note for note: 77 notes, 33 bars, F1 1.000 on pitch, start and duration (`OnDeviceSoloTest`).
- **The band draft** (`pitch/BandDraftPipeline.kt`, design/system.md §3) is the engine's `brass-band` profile with `muscriptor=false`: Basic Pitch on the whole mix fills the melody, bass and harmony slots of the core's song arranger (`arrangeSongWith`, no melody support), Beat This! small gives the beats, and the result is the small band or the quartet. Without a beat grid it stops, as the engine's song arranger does. A brass band recording goes to the computer when it is there (paired, and Connected or Reconnecting); otherwise it is made on the phone, labelled a draft, in a foreground service (`DraftService`: `dataSync` below Android 15, `mediaProcessing` from 15). A take longer than free memory holds (`BandDraftPipeline.fits`, against `ActivityManager.MemoryInfo.availMem`) is refused before it starts. A finished draft opens on the score rather than in Check the notes (`Product.afterTranscription`): Basic Pitch alone hears its melody, so every melody note is marked "?". A saved draft keeps its recording beside it, and **Make the full score** sends that to the computer as a new brass band score. `BandDraftTest` runs the draft on the ten ChoraleBricks quartet mixes against the engine's draft (`apps/apple/scripts/make-band-draft-reference.sh` writes it to `data/runs/apple/<name>-band-draft-ref`): what is heard agrees (pitch and onset within 50 ms), and on the engine's beats the written score agrees too; Beat This! on ONNX and on PyTorch can still place a downbeat differently in a fermata, which shifts the bars of that piece.

## Design system

Each app wears its product's design system: Brasscribe's (`design/`, generated into `design/dist/`) or Fretscribe's (`design/fretscribe/`, generated into `design/fretscribe/dist/` under the same Kotlin names, so the screens are shared; `design/fretscribe/tokens/README.md` has the map).
- **Wiring** (`app/build.gradle.kts`): per product, the Compose theme and icon enum compile straight from `<dist>/android/kotlin`; `sync<Product>DesignResources` syncs the `ic_bc_*` icons, the display face (as `res/font/display`) and the adaptive launcher icon (with its monochrome layer) from `<dist>/android/res` and `<dist>/icons/android/res` into one generated res folder, and the font licence goes to the assets. Nothing is hand-copied, so a token change is a rebuild. The window colours behind Compose are the product's token `bg`, in `app/src/<product>/res/values/themes.xml` (a test in `design/tokens` keeps them equal to the tokens).
- **Fretscribe's look** is checked by `FretscribeThemeTest` (`app/src/screenTestFretscribe`): Home in light, dark and high contrast has its paper and its blue-ink mark, and the titles are Atkinson Hyperlegible Next.
- **Theme** (`ui/theme/Theme.kt`): `PlayTheme` is `BrasscribeTheme` with the display face. Primary is ink (paper in dark); the cursor purple, the uncertainty colours and the loop tint are for the score only. Instrument Serif is used only for `displaySmall` (36 sp screen titles) and the wordmark; everything else is Roboto, in sp, so it follows the font scale.
- **Components** (`ui/Common.kt`): one `PrimaryButton` per screen (52 dp, 12 dp corners, pinned above the navigation bar), tonal/outline/plain buttons, list-row groups with icon wells, practice chips (on = tonal fill, ink edge and a tick), the info note, the brand mark, and the "?" / boxed "?" mark.
- **Screens** follow `design/mockups/png/*phone*` in the Material idiom: first run, Home (one primary, the other ways in as rows), What is this? (choice cards, "where it runs" with Change), making the score (the steps, brass progress, a confirmed Cancel), Check N notes (one note at a time, Keep and Skip, Finish later with a confirm), How should the score be?, the score with its toolbar and a player that wraps and never clips, Share or print (Print as the primary), errors with a way forward, and Settings.
- **The score** colours each uncertain note (head, stem, flags, accidentals) from the tokens, and `score/NotationOverlay.kt` draws its mark from alphaTab's layout (`boundsLookup`, note bounds on) inside alphaTab's scrolling render wrapper: a "?" 1.6 staff spaces tall, and for a very uncertain note (MusicXML `enclosure="rectangle"`) the same "?" in a box with a stroke of at least 1.5 dp. alphaTab's own small text mark is blanked, so its text band still keeps the space. A second overlay under the notation draws the ad-lib tint behind the free-time bars ("ad lib." up to "a tempo"); the loop tint replaces it in a loop, and high contrast has no tints. Measured on the emulator: the mark is 1.6 staff spaces at 100 % (about 14.5 dp) and at 200 % zoom (about 30 dp). The marks are also the way to their notes: a tap inside the 48 dp target around a "?", above the staff, opens Check the notes at that note (the part it is on, when that part follows a recording layer, else the tune; the note of that bar nearest the mark; bars are counted as the score numbers them, without a pickup). A tap on the music itself, a drag, and every tap on the music stand stay alphaTab's. For TalkBack and the keyboard, the score has the custom action "Check the ? notes in this bar" while the bar it is at has a mark. Check the notes keeps its place for each score while the app runs (the part, the card, the notes put off), so Check them goes on from there.
- **Share or print** offers My part (the player's seat, e.g. "Solo Cornet (you)", the default, with PDF), Every part (one file per player) and the conductor's score, as on Windows. The labels follow the lineup the score was arranged for: a quartet offers "1st Cornet (you)", Every part and "Score (all 4 parts)", since it has no conductor. Part PDFs and braille come from the engine's `parts/NN-Name.*` files; a part's MusicXML is cut from the score and its talking score comes from the core. Print sends one print job: one PDF as it is, and Every part's PDFs joined page after page into one (`export/PdfJoin.kt`, off the main thread). The join copies each file's objects as they are, so every page stays as the computer drew it; it reads the PDFs the engine writes (a classic cross-reference table, no object streams, encryption or appended updates), and for anything else it prints one job per PDF, as before. After a note is changed on the phone, the engine's braille and audio say "Made before your changes".
- **PDFs from the phone** (`export/PhonePdf.kt`): a score with no PDF from the computer (made on the phone, opened from a file, or changed on the phone since) gets one all the same. alphaTab engraves each part (or the full score) off the main thread with a canvas of its own (`PictureCanvas`) that keeps the drawing as an `android.graphics.Picture`, and Android's `PdfDocument` writes the systems onto A4 pages, so the pages stay vector and the music font is embedded. A part is drawn with its staff about 7 mm high, the conductor's score smaller (a system taller than a page is drawn smaller still); ink on white, the part's name over its pages, and the "?" legend under a page with a doubtful note. Every part writes a file per player and one file of them all, for one print job. Share or print says which PDF it is: "From Brasscribe on your computer" or "Laid out on this phone". The computer's PDF is used when it exists and nothing was changed. `PhonePdfTest` measures time and memory for a 25-part score on the JVM.
- **Check N notes** starts with the player's own part ("Check your part first"), very unsure notes first; Skip sends a note to the back of the queue. The accompaniment layers are folded under one chip. The note card shows the bar on a staff (`score/BarSnippet.kt`, alphaTab without a player) with the note ringed. Change note… offers a semitone, an octave and what each transcriber heard, re-arranges the score through the core and stays on the changed note after Save (the golden Composition re-arranges to the golden score, part for part: `RearrangeTest`).

## Features and where they live

- **Inputs** (`ui/HomeScreen.kt`, `capture/CaptureService.kt`, `audio/`):
  - file import through SAF
  - the share sheet (`ACTION_SEND`) and "Open with" (`ACTION_VIEW`)
  - video, whose first audio track is decoded
  - the microphone through Oboe
  - other apps' playback through AudioPlaybackCapture. Play shows an opt-out and DRM notice first, asks for MediaProjection consent, and runs a foreground service of type `mediaProjection` (type `microphone` for mic recording). After 5 s of silence it shows "Nothing is coming through…". Android offers no API that reports an app's opt-out, so silence is the signal.
- **What do you play?** (`ui/WhatDoYouPlayScreen.kt`, `MyInstrument.kt`) asks the player's instrument and part once (and in Settings), or "I conduct or listen". The score opens on that seat's part, in the clef the seat reads; each score keeps the seat it was made for when the instrument changes later. A seat the lineup has no part for gets the part it maps to, and says so (a trumpet takes the lead part). The tune is only offered to seats the core says can carry it, and a solo take for the percussion seat is refused up front with the reason.
- **Your instrument** (Fretscribe; `app/src/fretscribe/.../fret/`) takes the place of What do you play?: `Product.Root` shows it where Brasscribe's screen would come, after the first run and from Settings, `Product.instrumentValue` is the value on the Settings row, and `Product.BAND_SOUNDS` leaves the Sound choice out of Fretscribe's Settings (it has no band sounds). One question per row, each a picker row that is one element for a screen reader and for the keyboard (Tab, Enter or Space, arrows in the picker, Escape; the focus ring is drawn by the screen itself): instrument (guitar, bass, ukulele, mandolin), its strings (a guitar and a bass; a ukulele is asked its size instead: soprano, concert or tenor, or baritone; a mandolin is not asked), usual tuning (the `target-fretted` presets of that instrument, its usual one first: a ukulele's are High G and Low G; an instrument with one tuning has a row that says it and opens nothing, and a baritone ukulele's and a mandolin's are named by their strings, "D G B E" and "G D A E"), which hand is on the neck, and what you read. Another instrument starts in its own usual tuning. Each visit starts from what is stored: choices left without Save are not picked up again, also after the app was stopped and restored. Nothing is kept until Continue or Save, and Not now leaves a six-string guitar in standard tuning, read as tab. `YourInstrument.jobOptions()` gives the `tab` job's `instrument`, `tuning` and `layout`. A bass stored by the version that offered only the bass still reads as that bass. A capo is not asked here: it is a song's, and Check the song asks about it. Like What do you play?, it is asked only when the native core is in the build. Its tests are `YourInstrumentTest` (`app/src/testFretscribe`) and `YourInstrumentScreenTest` (`app/src/screenTestFretscribe`), both run by `./gradlew testFretscribeDebugUnitTest`.
- **Note names in bokmål.** The note B is H in Norwegian (and B is B flat), so the tunings are «Drop H», «HEAD» and «D G H E» there; E flat is Ess.
- **Fretscribe's words** are string overrides in `app/src/fretscribe/res/values` and `values-nb`: a string there replaces Brasscribe's of the same name. The first run, Home, Your instrument, Settings, What is this?, the transcribing steps, the problems on the way to a tab, Check the song and the tab view are in Fretscribe's words. Lint does not notice an override that is missing in `values-nb`, so add both.
- **Home in Fretscribe has no Open a tab** (`Product.OPENS_SCORES`): an imported MusicXML file would open on Brasscribe's score screen, not in the tab view. A MusicXML file opened with Open a recording, from the share sheet or with "Open with" is not opened: a problem screen says "Fretscribe can't open sheet music yet", with Open a recording and Record with the microphone as the ways on (`Problem.SHEET_MUSIC`). It is a screen and not a line on Home, as a file that starts the app is there before Home is drawn. What is sheet music is told by the file's name (`.musicxml`, `.mxl`), the type it came with, and otherwise how it starts (`SheetMusic`), so an `.xml` that is no MusicXML is a file that could not be read. Its tests are `SheetMusicTest` (`app/src/test`) and `FretscribeSheetMusicTest` (`app/src/screenTestFretscribe`).
- **A recording becomes a tab** (Fretscribe; `fret/TabSong.kt`, `WhatIsThisScreen.kt`, `CheckTheSongScreen.kt`). What the two apps do differently goes through `Product`, and `PlayViewModel` asks it in a few places: `Product.job` completes the job that is sent, `Product.audioOnComputer` names a recording the computer already holds (then nothing is uploaded), `Product.afterTranscription` names the screen that follows, and `Product.makes` says which of the computer's scores open here.
  - **What is this?** has two choices: Just my instrument (`recording: "instrument"`, no separation) and A full song (`recording: "song"`). For a guitar or a bass nothing is chosen until the player chooses. A ukulele or a mandolin starts on Just my instrument, as the computer takes them, and A full song says that it only works when no guitar is playing (the computer finds them where it finds a guitar). The answer stays with the recording while it is the one in hand (`SongAnswers`, in memory: after the app was ended in the background it is asked again). Continue needs an answer, the computer and the recording's file. Both are written down by the computer in this version, so the row under them says whether it is there, with Connect (the pairing screen, or another try at a paired computer) when it is not; nothing is offered on the phone.
  - **The job** is `tab` with the player's instrument, tuning and layout, the answer, capo 0, octave auto, and the computer's defaults for the fingering style and the chords (as they were heard), which are not sent (`tabOptions`, `tabJob`). The profile id is the one the computer has for the instrument (`tabProfile`, from the computer's `/v1/profiles`, asked when What is this? and Check the song open): `tab` where it has it; `bass-tab` for a bass on a computer from before the `tab` profile, or when the computer could not be asked. Continue waits for the computer's answer ("Asking your computer…"), and what one computer said is never used for another (`ComputerProfiles`). A guitar, a ukulele or a mandolin on such a computer is refused before anything is sent, on What is this?: "Fretscribe on your computer is too old to write guitar tabs. Update it there.", and Check the song offers no change there, with the same words. `TabJobOptionsTest` asks the engine's own option check (`profiles.job_options`, through `apps/android/scripts/check-tab-options.py`) about every job the screens can produce; it skips itself where pixi or the engine is not set up. The transcribing screen is the shared one; the tab's `notes` stage is the step "Placing the notes in bars". In Fretscribe it names the computer ("Fretscribe on Kari's Mac is writing down the notes"), says to keep the app open and holds the screen on meanwhile (nothing tells the player when a tab is ready while the app is away), and shows no time left (`Product.TIME_LEFT`: the estimate counts stages, and a tab's stages differ too much in length).
  - **Check the song** follows (drawn in the place of Brasscribe's output choices, `Screen.OUTPUT`): the rows `SongCheck.rows` finds in `EngineApi.tab(jobId)`: the tuning, with the one that fits better and **Use …** when there is one; the capo, for a guitar and a ukulele, with **Change the capo** (no capo, or fret 1 to 12, in a picker) and a line that says what a change does (the frets change, the notes stay the same: the computer has no way to keep the shapes instead); the octave when the line or single notes were moved; the reference pitch when the recording is more than 10 cents off; key and tempo; notes marked "?", notes with no place, notes left out because they can't be played with the rest, and notes added to complete a chord (the app never asks for those). A row's button has the song written down again with that changed, for this song only: a new job on the recording the computer already holds, with the options the tab was made with (`SongCheck.optionsOf`, read back from the result and its job's stages). So it also works for a song opened from Your songs, after the app was ended in the background, and when the phone's copy of the recording is gone. "You can change this later." is only said when a row offers a change and the computer is there. The other choices of the design (Other… tunings, the key and tempo) are not built yet. **Show the tab** opens the tab view.
  - **The tab** (`fret/TabScreen.kt`, `TabView.kt`, `TabIndex.kt`, `TabMarks.kt`; design/fretscribe/system.md §3) is Fretscribe's own screen where Brasscribe shows a score (`Screen.SCORE` for a tab, in `Product.Root`). It is the view to read and the place to practise (below).
    - **The page** is `tab.musicxml` engraved by alphaTab without a player, in the song's layout (tab with stems for the rhythm, tab and notation, or notation), full width, in the theme's colours: ink numerals, the lines in the `string` colour. In a pair of staves the rhythm is read on the notation staff, so the tab staff has no stems. alphaTab 1.8.4 reads the second staff of a pair into its fifth voice and draws a rest for the empty first one, over the numbers; `TabView` makes the voice with the music the bar's first.
    - **One scroll.** alphaTab scrolls its own page (it only draws the lines in view), and the screen's scroll moves it: a column of the page's own height (the height of alphaTab's scroll content, so both end at the same place) lies over the page with the marks' elements, takes the drags, the keyboard's focus and the screen reader, and puts alphaTab's page where it is. alphaTab's own scrolling to its cursor is off. Page Up, Page Down, Home and End move the page, also before anything on the screen has the keyboard's focus (the screen takes it when it opens).
    - **A view has one size, one width and one set of colours.** Another zoom, text size or theme is a new `TabView`, a quarter of a second after the last step, and so is a turned phone (the activity is not made again when it is turned). The page is engraved once the view has a width: alphaTab skips an engraving asked of a view without one. alphaTab lays its page out in steps and keeps track of the lines in view by the scroll steps it sees: a page engraved again under a scrolled view, or while the last engraving was still being laid out, came out blank or half laid out now and then.
    - **The bar being read is kept**: through a turn of the phone, a new size, and a visit to Check the song (`TabPlaces` while the app runs, the saved state after it was stopped). The page is put at the line with that bar after every engraving; only the player's own scrolling changes the bar.
    - **Size.** At 100 % the fret numbers are 1.5 times body text (`TabTokens`, from the `tab` tokens), and they follow the system's text size; zoom is 50 to 400 % on top of that (`TabSize`). A larger page has more lines of fewer bars and never scrolls sideways. The size stops where the page would be narrower than `TabSize.MIN_PAGE_UNITS`: past that alphaTab presses the notes of a bar together. A bar with many notes can still be tight at the largest sizes; scrolling one bar sideways inside its own region is not built. On a screen wider than it is tall, a larger text size does not make the page larger than two lines to the screen (a line's height is reckoned from the strings and the layout, `TabSize.lineUnits`, so the size is known before the page is engraved and it is engraved once), and not smaller than at the ordinary text size: on a phone on its side that is the ordinary size (at 200 % a single line would be taller than the room), and the zoom still enlarges it.
    - **Fret numbers are set in Fretscribe Tab** (`design/fretscribe/brand/fonts`, bundled in the Fretscribe app only, in its assets with its licence). alphaTab draws with alphaSkia on Android, which finds a face by family name; `AlphaSkiaTypeface.register` (alphaSkia's own Java API) adds one from its bytes, and `RenderingResources.tablatureFont` names it. alphaTab's wrappers around that (`SkiaCanvas.registerFont`, `AndroidCanvas.registerCustomFont`) are not public in the Android build. `TabViewTest.theFretNumbersAreSetInFretscribeTab` measures a drawn 0 with and without the face.
    - **The header** has the tuning chip ("Standard · no capo", a button whose name reads the whole state), the tempo, and, when there are any, "N notes marked ? · Check them" and "N notes with no place". The page's own words over its first bar (the tuning, the strings, the capo) and its tempo mark are not drawn: the header says them, and a mark over the first notes would stand on them. The chip and the line open Check the song for now: the tuning and capo sheet and Fix a note are not built. The header stays above the tab while it takes a third of the room or less; on a phone on its side, or when it is taller than that, it is the top of the page and scrolls away with it, and the page opens on its first line with the header a scroll up away, so the tab and the player have the screen. Only with a screen reader explored by touch (TalkBack) does the page open at its top, the header read first; Switch Access and a service that only speaks are used by sight and get the first line. Once the player has scrolled up to half the header or more, a zoom leaves it in view. Practice is the same both ways: `PracticeBothWaysTest` opens the tab upright and on its side, at 100 % and 200 % text, and checks that a whole line of the tab is in view and that every control of practice and of the tab is shown whole and at least 48 dp.
    - **The marks come from the data** (`EngineApi.tab`), not from the page's words: a "?" in the doubt colour above the column of every note below the threshold (`tab.uncertain-threshold-default`, 0.4), with the numeral in that colour on the `uncertain-tint` wash, and a boxed "!" in ink above the column of a note with no place. High contrast has the shapes and no wash. alphaTab is given the page without its "?" and "!" words and without the doubt colour, so nothing is drawn twice. A marked beat gets blank text as tall as a mark, so alphaTab keeps a band for the marks above the lines that have any; they stand above the bar numbers. They are drawn by an overlay in alphaTab's render wrapper from `boundsLookup`, as the score's are. The two lines of the header count what is drawn: a doubtful note with no place is under its "!" and not counted as a "?", and a note the page folded into another is in neither.
    - **Which drawn note is which.** The core writes `<?fretted-note N?>` on every note piece (core/target-fretted/README.md), and alphaTab drops processing instructions, so `TabIndex` reads the MusicXML itself: for each piece its note, staff, measure (counted as written, so a pickup is the first), start in the measure, beat (by the time signature in force there; a pickup's beats are those of the bar it leads into), string and fret, and whether a tie comes into it. A marked note's column is its first piece on the tab staff (the notation staff when it is the only one), and alphaTab's beat is the one in that staff and bar with the same start (`Beat.playbackStart`), in any voice; the numeral is the note of that beat with the same fret and string (alphaTab counts strings from the lowest). A note without a place has no index on a tab staff (it is a rest there, or left out of its chord): it is found through its index on the notation staff in a pair of staves, and otherwise through the page's boxed words, taken in order. What cannot be matched is counted (`TabMarks.unplaced`, `TabView.unmatched`) and not drawn: a note the writer folded into another (two notes of one pitch on one place are written once), boxed words and notes without a place that do not agree in number, or a beat alphaTab reads at another start than the page writes.
    - **Without the computer** (a saved song, the computer away) the tab's data cannot be read, and the marks are the page's own: the `<?fretted-confidence?>` of its doubtful notes and its boxed words. The page then names a note without a place and not why it has none.
    - **Each mark is an element** of at least 48 dp over its column, in reading order, for touch, the keyboard (Tab, then Enter) and a screen reader. Its name says the note: "Bar 3, beat 2. 3rd string, fret 2, B. Fretscribe isn't sure about this one.", "The pickup bar, beat 4. …" or "Bar 7, beat 2. D1 is lower than your lowest string. Is the tuning right?". A tap shows that sentence under the tab (a polite live region). The other pitch a doubtful note could be is not said: the tab's data has other places for a note, not other pitches. The tab itself is one element that says the title, the layout, the tuning, the tempo, the bars and how many notes are marked; reading it beat by beat is not built.
    - **Share or print** is not offered from the tab yet: the export sheet is written around the band's files (`brass-band.pdf`, parts, braille) and needs its own change for a tab's.
    - `apps/fixtures/bass-line-marks` is the bass line with notes to check: a doubtful note, a doubtful note written as tied pieces, and a note below the lowest string, in the three layouts (`make-bass-line-marks.py` changes three of the notes the engine heard and has the engine place and write the line again). `apps/fixtures/tab-probes` are short hand-written lines that each put the marks in a hard place (chords with a doubtful inner note, a tie over the bar line, notes moved to the grid, a pickup, triplets, a note with no place in a chord, a capo, six-eight), in the three layouts (`make-tab-probes.py`). No audio or models are involved in either.
    - **Practice** (`fret/PracticeBar.kt`, `PracticeModel.kt`, `RecordingPlayer.kt`, `TabClock.kt`; design/fretscribe/flows.md §9) is on the same screen: the recording is the sound.
      - **The player** under the tab, in the design's order: Play (64 dp, the primary), back to the start (of the repeat), a bar back, a bar on, "Bar 13, beat 2", the speed with a step down and a step up, and Repeat bars. It wraps onto as many rows as it needs (one on a phone on its side) and never clips. The speed moves in steps of 5 % from 25 to 150 %, and the pitch stays the recording's.
      - **The recording plays through Media3's ExoPlayer** (`androidx.media3:media3-exoplayer`, a dependency of the Fretscribe app only): it reads the files the app takes in, stretches time without moving the pitch, seeks to the millisecond, asks for the audio focus and pauses when headphones are pulled out. While the phone takes the sound away for a moment (a call, another app's announcement) the player shows Play, the cursor rests and the screen may sleep; the recording goes on by itself after. Leaving the tab or the app stops it; the screen stays on while it plays.
      - **The tab follows the recording by the beats the computer tracked** (`Tab.beat_times`, the second of every quarter note, with `first_downbeat`): one step of `beat_times` is `ticks_per_beat` ticks, a written quarter note in every time signature (a bar of six-eight is three steps). `TabClock` turns a second into a bar and a place in it, and back, with the lengths of the bars read from the page (`TabIndex.measures`; a pickup is the first bar). Where the first bar starts against tick 0 is read off the page too, from the notes' starts in the data against where they are written. A song opened without the computer has the same beats in the notes saved with it. alphaTab's player is not used: the tab view is still engraved without one, and a new view for a new size or theme takes the cursor and the repeat from the screen.
      - **The cursor** is a 3 dp line in the cursor colour at the left edge of the column of the beat that sounds, with a wash behind the column; it moves from beat to beat (also with the animations turned off), so nothing is drawn while a note sounds or while the song is paused. The page goes to the line being played when the cursor reaches it, with the lines to come under it, and to where the player moved the song when that is out of view. "Bar 13, beat 2" changes with every beat while the recording plays and is a live region only when it does not: a screen reader hears it when the player moves the song and when the recording stops, not during playback. A change of speed is said.
      - **Repeat bars** opens a dialog with the first and the last bar, each with a step down and a step up (nothing is dragged), starting on four bars from the bar the song is in. The bars get a band behind them and a bracket at each end in the repeat colour, with a rail under the bars on every line they run over, and the chip says "Repeating 12–16" (its words are its name); high contrast has the brackets, the rail and the cursor's line and no washes. The recording turns back at the end of the last bar (a message on the playback thread at that millisecond), and a bar back or on stays inside the bars. In the last bar (of the tab or of the repeat) a bar on does nothing. A repeat of bars past the end of a recording shorter than its tab is not turned back to: the recording stops at its end.
      - **Keys.** Space plays and pauses, unless a button in focus takes it as its own press. With the screen itself in focus (as it is when it opens) or one of the tab's marks, the left arrow goes back to the start of the repeat (a bar back when nothing is repeated) and the right arrow a bar on. Page Up and Page Down still move the page.
      - **The recording on the phone.** A song the phone sent has its file in hand; the first time its tab is opened the file is copied to the app's own folder (`noBackupFilesDir/recordings`, by the job's id, left out of backups), so the song can be practised when it is opened again. A song opened without it (from the computer's list, or on a phone that never had it) says "The recording is not on this phone." and offers **Get it from your computer** when the computer is there: `EngineApi.jobInput` (`GET /v1/jobs/{id}/input`) writes it to that folder, up to 2 GiB (the largest upload the engine accepts by default, so everything it was sent fits). The player says which it was when it does not come: the computer no longer has it, the computer could not be asked, the phone has no room, or it is too large; the tab can still be read. One fetch runs at a time, and leaving the tab gives it up. A file is named by what a file name can hold of the job's id and a short hash of the whole id; what a fetch or a copy that did not finish left behind is deleted before the next try and when the recordings are gone through. The recordings of songs that are no longer in Your songs are deleted the next time a song in the list is opened.
      - The song is kept where it was, with its speed and its repeat: for each song while the app runs, and for the last one through the app being stopped.
      - Not built: count-in and metronome, Sound (Tab, Both), the speed trainer and 1 % steps, saved repeats, hiding the controls while it plays, Lock the tab, pedals, and the line that scrolls past a fixed cursor (the page layout is the one the tab is read in).
      - Its tests are `TabClockTest` and `PracticeRecordingsTest` (`app/src/testFretscribe`) and `PracticeTest` (`app/src/screenTestFretscribe`), which makes its own recording (a tone on every note of the fixture's tab) and checks on the screen that the cursor is at the beat the recording is at while it plays, that half speed is half as fast with the pitch factor at 1, that chosen bars repeat, that a song without its recording says so and gets it from the fixture computer, the keys, and that a paused song draws no frames (on a device).

- **A job on the computer while the player is away** (`ComputerJobService.kt`, both apps). The job runs on the computer whatever the phone does: leaving the app, the phone ending it, or the app being swiped away never stops it (only Stop does, `DELETE /v1/jobs/{id}`; a dropped event stream does not), and once it is finished it is listed in Your scores / Your songs from the computer while the phone is connected to it (the list holds finished jobs only). Before the recording is sent, a foreground service of type `dataSync` starts with a quiet notification, so the upload and then the job go on while the player is away (the app is neither frozen nor ended). That is its only start in the foreground: the job, which may be made after the player has left, is told to the running service inside the app (`ComputerJobService.follow`), since the phone refuses a second foreground start from the background. The service is in the foreground exactly while a recording is being sent or a job is followed: no job made (the upload failed, or the app was closed meanwhile) lets it go, and so does the end of every job it follows. It asks the computer for each job, every 5 s for five minutes and then every 20 s (`JobFollow`), and stops following one after ten minutes with no answer, saying the score will be in Your scores when the computer is back. A job started while an earlier one is still followed does not take its place: each gets its own notice. When the job ends while no screen of the app is in front (`AppInFront`), it posts "Your score is ready" / "Your tab is ready" (or "couldn't be made") on its own channel, one notice per job, without the song's name on a locked screen that hides private content; the notices are cleared when the app comes to the front. Notifications are asked for once, on the transcribing screen at the first job on the computer (`AppContainer.notificationsAsked`), never at the first run; the screen says the player may leave, and promises a notification only when they are allowed. On the JVM, `ReadyNotificationTest` checks the words, the one question, the notification and its tap, and runs the service itself: one start in the foreground for a whole job, a job handed over while the app is away, two jobs at once, and the service let go when sending fails or is cancelled. It announces the title, the part and "bar n of m", and has the custom actions Next/Previous bar, Next/Previous part and Play this bar. The Text tab is the talking score: one item per event, with Next/Previous bar, Read bar and Play this bar.
- **Band SoundFont**: every part gets its own MIDI channel (drums on channel 10; alphaTab's own two-channels-per-track numbering wraps past 16 and shares presets), its preset at (bank, program) and its `channel_gain_db` from `sounds/mapping.json` (bundled as an asset), and the importer's per-beat instrument and bank changes are removed. The SoundFont itself is read from the app's `sounds/` folder. The full `brasscribe-band.sf2` runs alphaTab out of Java heap (its synth keeps every sample as floats: OutOfMemoryError at the 576 MB large heap with the 149 MB 16-bit file), so `scripts/mobile_soundfont.py` makes `brasscribe-band-mobile.sf2` from it: the same presets, desk variants and kits, sustain presets only, resampled to 22.05 kHz with the loops rebuilt (67.8 MB in the pinned `sounds-2026.09.30` pack, which publishes both files; drum samples with real energy above 11 kHz keep their own rate). Listen to this bar plays through the same SoundFont.
- **Realistic sound**: every pitched part plays an SFZ instrument through sfizz on its own channel with its band balance, humanized by the core (per player lag, timing and velocity, the soloist leading) and scheduled into the sfizz output sample-accurately (`score/HumanizedPlayer.kt`, 250 ms lookahead, following alphaTab's position and speed). Percussion stays on alphaTab's kit, as in the reference renderer. Each part loads `sounds/<instrument>/<instrument>-sus.sfz`; parts without one play a test tone.
- **Installing sounds**: the app creates `Android/data/no.brasscribe.play/files/sounds/<instrument>/samples` on first start. Files copied in with adb land readable only inside folders the app created, so copy into those, for example `adb push data/sounds/built/cornet-a/. /sdcard/Android/data/no.brasscribe.play/files/sounds/cornet-a/` and the SoundFont into `sounds/`.
- **Exports** go through the share sheet or "Save to Files":
  - MusicXML
  - PDF and MP3, from the engine
  - MIDI, generated by alphaTab from the loaded score
  - talking-score HTML from the core's talking score of the arranged score (every part)
  - braille (BRF) from the engine (`getBraille`); the core does not write braille
- **Languages**: English and bokmål (`values-nb`), with per-app language through the generated locale config. Lint fails on a missing translation.

## Testing

Most of the app is tested on the JVM, in the unit tests, in seconds, with no emulator. The real activity, view model and screens run there under Robolectric (native graphics), on a phone of the emulator's size with a status bar and gesture navigation, against a fixture computer (`FixtureEngineApi`, `apps/fixtures`) and the host build of the Rust core (without it the screen tests are skipped, with the reason; `scripts/check.sh` builds it first). alphaTab engraves there as on a phone, with alphaSkia's library for the machine the tests run on.

| Where | What | Command |
| --- | --- | --- |
| `app/src/test`, `testBrasscribe`, `testFretscribe` | plain unit tests | `./gradlew testDebugUnitTest testFretscribeDebugUnitTest` |
| `app/src/screenTest` (both apps), `screenTestBrasscribe`, `screenTestFretscribe` | the screens: flows, the score and the music stand, the tab and practice, the keyboard, 200 % text, bokmål, restored state, with the accessibility checks | the same; they also run on a device |
| `BrasscribeScreensTest`, `FretscribeScreensTest` | the screen catalogue: every screen in light, dark, high contrast, 200 % text, on its side and in bokmål, with the accessibility checks, no text cut off at 200 %, the keyboard in reading order, and a screenshot | `scripts/screenshots.sh compare` |
| `app/src/androidTest*`, `audio/src/androidTest` | what only a device can do (below), and a smoke test per app | `scripts/device-tests.sh smoke` or `device-only` |

The screen tests (`screenTest*`) are one source for two runs: the source sets are added to both `test` and `androidTest`. What differs between the JVM and a device (the text size, the language, a turn, the contrast setting, a key, a recording to open, waiting, screenshots) is behind `ScreenDevice`, which `src/test` and `src/androidTest` each have their own of. On the JVM time is the test's to move: `waitUntil`, `settle` and `rest` pass it. The rule is Compose's v2 test rule, whose effects run on a StandardTestDispatcher: an effect's coroutine that comes back from `Dispatchers.IO` resumes on the main thread, as on a phone. A sound played through an AudioTrack (the recording in practice) plays out by the clock on the wall, as on a phone (`PlayingAudioTrack`, in `robolectric.properties`): Robolectric's own AudioTrack counts every byte it is given as played at once.

**Accessibility.** Every screen test runs the Accessibility Test Framework's checks on the whole window (touch targets, a missing or repeated name, traversal order, and contrast against a picture of the screen; low contrast fails) on the screen it ends on, wherever it calls `checkAccessibility()`, and on every screen of the catalogue; on a device also on every action. (The framework's check of links in text runs only below Android 8.) `ScreenAccessibility.known` lists the findings that are not real, each with its reason; it can let through only the framework's estimates (warnings), never an error. `ScreenAccessibilityTest` shows that the checks find what they should. The catalogue also checks that no text is cut off or ellipsized at 200 %, nor cut by a box it is in, also where a part that scrolls has it out of view (only what that part's viewport hides is not a cut; `cutAtLargeText` lists the texts known to be cut, each with its issue), that Tab reaches everything a finger can act on in the window it is in, also what Tab has scrolled out of view by the end of its round (`notReached` lists the known misses by their words and role, each with its issue), and that Tab goes through a screen in the order it is read: the top bar, the content, then what is docked under it (a screen's one primary button); a screen whose own order differs says why in `ownOrder`. `ScreenChecksTest` shows the reach and the cut-text checks failing on screens made to fail.

**Screenshots** are not kept in git. `scripts/screenshots.sh compare` takes the catalogues' screenshots at the merge base with `origin/main` and then on the branch, on the same machine, and writes `app/build/reports/screenshots/` (`index.html` with before, the difference and after for each changed screen; `summary.md`). It exits 1 when a screen changed, appeared or went away, 2 when the catalogues' own checks failed, and 3 when the screenshots could not be taken at the base (nothing was compared). CI does the same on every pull request: a changed screen fails the screenshot job, and its images are in the `android-screenshots-<app>` artefact; when the change is meant, the label `screenshots-changed` on the pull request lets it through. Adding or removing the label starts CI again, and the job reads the pull request's labels as they are when it runs (a re-run of an older run sees them too), only when screens changed, in a step of its own that runs none of the pull request's code. The label never lets a failed check or a failed base through. A screen that is a moment of something under way (`steady = false`) has no screenshot. About shows a fixed version (0.0.0) in the catalogues, not the app's own, so a release does not change its pictures. **The notation's colours are wrong in the screenshots, on purpose:** alphaSkia's desktop build swaps red and blue in everything alphaTab engraves, so the staff and the uncertain notes come out in other colours than a phone shows (a blue "?" over an orange note, for one). The rest of the screen is drawn right. A colour change in the notation is therefore checked on a device, not in the screenshots (see below). The flows' own pictures (`shot(...)`) are for looking at: `scripts/screenshots.sh record` keeps them in `app/build/outputs/screen-pictures`.

**What the JVM does not show, and stays on a device** (`@DeviceOnly`, `scripts/device-tests.sh device-only`):
- the sound out: Oboe and sfizz (`RealisticSynthTest`, `OutputStageInstallTest`, `PlaybackLevelTest`), the score playing in real time (`MusicStandPlaybackTest`), and how fast practice goes by the wall clock (`PracticeTest.halfSpeedIsHalfAsFastByTheClock`; the JVM checks that it plays, and the speed and pitch the player itself runs at)
- capture: the microphone and MediaProjection (`MicTakeTest`); a foreground service (`DraftServiceTest`); the phone's own decoding of a recording, a large video among them (`LargeVideoImportTest`; on the JVM a recording's sound track is handed to Android's stand-in media classes)
- the PDF document the phone writes (`PhonePdfDeviceTest`: Robolectric has no `PdfDocument`; the JVM checks the engraving and the pages drawn, with `JvmPdfPages` in its place)
- memory (`ScoreMemoryTest`, `SoundFontMemoryTest`, `BarAudioMemoryTest`) and the frames the system counts (`TabFramesTest`, `PracticeTest.aPausedSongDrawsNothing`)
- the audio focus: a call that takes the sound pauses practice (`PracticeTest.aCallThatTakesTheSoundForAWhilePausesTheSongAndItGoesOnAfter`; Robolectric's audio manager does not tell the player its focus is lost)
- alphaTab's page after a turn of the phone (`TabViewTest`'s two turned tests: on the JVM the turn is told to the activity by hand, and the page ends a line off or undrawn) and the colours of what alphaTab engraves (alphaSkia's desktop build swaps red and blue, so a doubtful numeral is checked in its colour on a device, `TabViewTest.theDoubtfulNumeralsAreDrawnInTheDoubtColour`; on the JVM the colours the tab view is given and asks alphaTab to engrave are checked, and ink and the lines on both); the system's monospace face (`TabViewTest.withoutItsFaceTheFretNumbersAreInTheSystemsMonospace`)
- what is said to a screen reader as an announcement (`PracticeTest.thePlaceItStopsAtIsSaidOnce`), and an upgrade over an older installed build
- the per-app language setting: the generated locale config (`locales_config`) is read by the system's settings, which the JVM does not have; the JVM switches the app's language itself
- by hand, on a real phone: TalkBack's speech (`qa/screen-reader-scripts/talkback-android.md`), the sound by ear, and how it feels to use

The device smoke (`scripts/device-tests.sh smoke`, about two minutes for both apps) starts each app, makes a score or a tab from a recording the phone decodes itself, checks the score or tab has ink on the screen, and turns the phone. For an emulator of your own:

```sh
serial=$(apps/android/scripts/emulator-pool.sh acquire)
ANDROID_SERIAL=$serial apps/android/scripts/device-tests.sh smoke        # or device-only, or class <name>
apps/android/scripts/emulator-pool.sh release "$serial"
```

### Rules

- **JVM first.** A change is verified with `scripts/check.sh fast android` while working and `scripts/check.sh full android` before handing off (it adds lint, the debug builds and the screenshot comparison). A device only for the cases above, and the smoke before a release or a change to what runs on a device.
- **A new screen** comes with a JVM flow test in `screenTest<App>`, an entry in its app's screen catalogue (which gives it the screenshots and the accessibility, 200 % and keyboard checks), and `checkAccessibility()` where the flow shows it.
- **Reviewers** verify with the JVM tests and the screenshot report (CI's `android-screenshots-<app>` artefacts), and write a probe as a JVM screen test, not as a run on an emulator.
- **A found problem** that the change does not fix is an issue, and an entry in `ScreenAccessibility.known`, `cutAtLargeText` or `ownOrder` only with that issue named, removed when it is fixed.

The export test shares MusicXML, MIDI, the talking-score HTML and the PDF and checks them, plus the braille file when the fixture has the engine's render of it (it has none now; the PDF is then the phone's; Robolectric has no `PdfDocument`, so on the JVM the pages are drawn and the file stands in for it, `JvmPdfPages`, and `PhonePdfDeviceTest` checks the real one on a device; Listen to this bar also needs the engine's MP3, so that test is skipped without one). `audio/src/androidTest/.../RealisticSynthTest.kt` renders sfizz offline. For the SFZ case, pass `-Pandroid.testInstrumentationRunnerArguments.sfz=/data/local/tmp/sounds/cornet-a/cornet-a-sus.sfz` after pushing an instrument there.

Screenshots of the design (light, dark, bokmål and 200% text) are in `docs/screenshots/design/`; the ones from before the design system are in `docs/screenshots/before-design/`.

The TalkBack acceptance script (`qa/screen-reader-scripts/talkback-android.md`) still needs a person with TalkBack on a device. Automated checks cannot hear speech.

## Known limits

- **Realistic tier sync.** The humanized schedule follows alphaTab's position events and a wall clock. The offset between the sfizz output and the cursor has not been measured.
- **alphaTab 1.8.4 on Android** has three more bugs worked around here: `api.loadSoundFont(ByteArray)` returns false for the same `when` reason as `load` (the app hands the bytes to `api.player` directly); registering on `api.midiLoaded` recurses forever in `AlphaSynthWebWorkerApi.loadedMidiInfo` (the app re-applies channel volumes on `postRenderFinished` instead); and it cannot hold the full band SoundFont (see above).
- **Beat grid of solo takes.** On the URMP clips Beat This marks most beats as downbeats, so both the engine and the phone write 1/4 bars; the engine's `arrange_solo` path and the phone agree on the notes (onset+pitch F1 0.963 on URMP March) but not on bar positions.
- **alphaTab's `api.load(bytes)`** returns false on Android: `AndroidUiFacade.load` uses `when (data) { (data is ByteArray) -> … }`, which compares values rather than checking the type. The app parses with `ScoreLoader.loadScoreFromBytes` and calls `renderScore` itself.
